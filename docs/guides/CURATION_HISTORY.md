# Append-only curation history

The curation-history layer is an append-only provenance pattern ported from
`monarch-initiative/dismech`. It answers the question other fleet records do
not: **which model, using which tool, changed what, why, and under which issue?**

## What lives where

| Piece | Path | Consumed how |
|---|---|---|
| Canonical LinkML schema | `src/kg_microbe_governance/artifacts/schema/history.yaml` | packaged with `kg_microbe_governance` and governed by the strict artifact manifest |
| Mech consumer copy | `src/<mech-package>/schema/history.yaml` | synchronized byte-for-byte from one immutable claw revision |
| Scaffolder and validator | `src/kg_microbe_history/` | installed as `kg-microbe-history` |

This follows the same shape as `kg_microbe_kgscan`: claw owns one
implementation and each Mech exposes thin repository-specific recipes.

The schema is **vendored** into every Mech; the scaffolder is **not**. Each Mech
validates its local schema copy so its correctness gate is self-contained and
pinned rather than dependent on another repository's current branch:

```bash
kg-microbe-history validate history \
  --schema src/<mech-package>/schema/history.yaml
```

The installed CLI resolves its default schema from
`kg_microbe_governance/artifacts/schema/history.yaml` package data, so it also
works outside a claw checkout. There is no legacy compatibility package or
source-tree fallback. Pass `--schema` only when deliberately validating a
Mech's governed copy or another compatible `HistoryRecord` schema.

To change the shared schema, update the canonical artifact and manifest in claw,
merge a reviewed claw commit, and coordinate that immutable pin across all five
Mechs. See [Vendored governance](VENDORED_GOVERNANCE.md) for synchronization,
audit, and rollback.

## Enforcement model

The DisMech-derived model is deliberately asymmetric:

- **Presence is advisory.** CI warns when a data record changes without a
  history record and still passes. A hard provenance-presence gate blocks
  legitimate work at inconvenient moments and trains contributors to route
  around it.
- **Validity is blocking.** Once a history record exists, it must be structurally
  and schema-valid.

## Design properties worth keeping

### Filenames are unguessable on purpose

Records use `<TIMESTAMP>-<actor>-<shortid>.yaml`, where `shortid` is generated by
`secrets.token_hex(3)`, inside a directory for the target slug. Two agents
curating the same record concurrently cannot collide, so this layer has no
shared-changelog merge-conflict surface. That property matters when the fleet
runs many concurrent sessions.

### Outcome is orthogonal to event type

`outcome` lets a `REVIEW` record that it found nothing (`no_change`) or an `EDIT`
record that it hit a wall (`blocked`) without multiplying event types.
`no_change` is a real result: it records that something was checked.

### Details are required

A record without `details` is only a timestamp. If `new` is called without
`--details`, it writes a TODO placeholder for the contributor to replace. Both
the CLI validator and LinkML schema reject that placeholder, so an agent cannot
scaffold a record, fail to return, and still pass the validity gate.

### Only YAML target kinds derive paths from slugs

Only `record` and `schema` targets can derive a path from `--slug`. Mappings may
be `.sssom.tsv`, reports may be Markdown, and infrastructure may be a justfile or
workflow. Those kinds require an explicit `--path`; append-only provenance must
not preserve a guessed extension forever.

### The record path is the final stdout line

Everything human-facing is written to stderr so callers can capture the path:

```bash
record=$(kg-microbe-history new \
  --kind record \
  --slug example \
  --target-root data \
  --summary "Reviewed example" \
  --details "Checked the record and found no required changes.")
```

The same contract is available through each Mech's `just new-history` recipe.
